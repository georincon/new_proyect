## 1. Resumen

Se desplegó, en un entorno Docker aislado, un registro de DID Documents para `did:web` (servicio Ktor + PostgreSQL detrás de nginx). Es **opcional y está apagado por defecto** (`VDR_ENABLED=false`). Con él apagado, la aplicación ni se conecta a la base de datos ni abre el canal de escritura, y el camino base responde igual. Incluye registro, actualización, trazabilidad, respaldo y restauración verificada.

## 2. Qué hay que entender (para exponer)

* **VDR** es un rol, no una tecnología: "el lugar donde se publican y consultan documentos de identificador". Puede ser blockchain; aquí es un **servicio web indexado por identificador**, porque `did:web` es así.
* **La forma del registro depende del método DID.** Para `did:web`, el DID *es* la dirección: `did:web:dominio:a:b` → `https://dominio/a/b/did.json`. Ese conocimiento vive en un **adaptador** (`DidMethodAdapter`/`DidWebAdapter`); si mañana hubiera otro método, cambiaría el adaptador y no el resto.
* **"Aislado, sin tocar el camino base"** se cumplió de tres formas: contenedores propios, solo nginx publica puertos (ni la base de datos ni la aplicación), y bandera apagada por defecto.

## 5. Decisiones, advertencias y límites

* **Bandera apagada por defecto y falla segura:** encender el VDR sin secreto JWT o sin clientes aborta el arranque (`AppConfig.init`).
* **El respaldo no contiene secretos** (los secretos de clientes viven en la configuración, no en la BD). Sí contiene el historial completo y la auditoría. Debe guardarse cifrado y con acceso restringido.
* **La restauración solo entra en un registro vacío**: evita mezclar historiales. Las operaciones de respaldo/restauración exigen cuenta administradora y mTLS.
* La entrada de auditoría `BACKUP` se escribe *antes* de exportar para que el propio respaldo la contenga.
* Cambio de método DID o de motor de almacenamiento: no probado; el adaptador está pensado para ello pero solo existe `did:web`.
* **No se desplegó en el dominio real**; TLS de laboratorio.
